Intro/What is TakeAny.AI?

What is TakeAny.AI?

TakeAny.AI is a self-hosted control layer for LLM agents. It runs as a single Go binary against a local SQLite database, on infrastructure you operate.

The host retains authority

The architecture rests on one principle: the host keeps authority. Provider credentials, policy evaluation, tool attachment, audit logging and retrieval all execute host-side. The model chooses among tools the host has exposed — it does not define its own execution policy.

An agent gets capability. The host keeps the keys, the policy, and the record of what happened.

Five defining properties

Five properties distinguish the design. They are the shape of everything else in these docs.

Agent / Ingress separation

An Agent defines behaviour — model binding, system prompt, attached tools, knowledge, session state. An Ingress defines exposure — transport, authentication, network rules, firewalls. They are separate records with a foreign-key relationship, so the same Agent can be exposed through different transports under different policies, or exist with no external exposure at all.

Depth of governance

Role-based access scoped to individual resources, with groups mapped from your identity provider and additional OPA policies, LLM safety firewalls at two independent boundaries, and fourteen log domains covering every runtime path. This is the property that separates TakeAny.AI from self-hosted automation platforms, which offer the deployment model without the control surface.

Selective isolation

Isolation is spent where the risk or dependency surface justifies it — browser control, document rendering, retrieval indexing and Python scripts run as isolated Firecracker workloads; host-native tool profiles handle everything else. The engineering judgement is where the boundary is drawn, not that one exists.

Layered policy enforcement

Five independent boundaries — host admin auth, transport ingress controls, LLM safety firewalls, isolated helper execution, and proxy-level network filtering — each enforced by host code, each independently logged.

Audit as a by-product

Fourteen log tables record agent turns, tool calls, model requests with token accounting, firewall verdicts, helper executions, job events, proxy traffic, remote commands, knowledge usage, script runs and authorization decisions. Traceability is a property of running the system, not a documentation exercise layered on top.

In short

One process, one database, on hardware you control. The model gets tools; the host keeps authority — and everything it does is recorded as it happens.

Intro/Architecture overview

Architecture overview

The entire control plane is one process. There is no message broker, no container orchestrator, no external cache, no separate vector database. State lives in SQLite and the filesystem.

This is a deliberate trade. It rules out horizontal scaling of the control plane, and it makes single-node deployment, backup and audit trivial — the correct trade for the regulated on-premise environments the platform targets.

Control planes

Separation is structural, not conceptual. Each plane has its own tables, its own service package and its own permission set.

OrchestrationSessions, Python scripts, Apps, the Scheduler, background jobs
AuditStructured logs across every runtime domain

The Agent / Ingress model

This is the central architectural decision. An Agent is a host-side configuration record — not a running process — carrying its own provider and model binding, system prompt, context-window and compaction settings, a tool-iteration limit, and firewall bindings. Tools and knowledge attach through explicit join tables, so an agent's surface is enumerable rather than inferred at runtime.

An Ingress binds an Agent to a transport. Two kinds exist: an api ingress exposes an OpenAI-compatible endpoint at POST /ingress/{slug}/v1/chat/completions with a bearer key, IP allowlist and firewall bindings; a webwidget ingress delivers a browser chat surface through a tunnel to the separate edge service.

Separating the two produces the properties regulated deployment needs: an Agent can exist with no external exposure; one Agent can be exposed through several ingresses under different policies; revoking exposure is deleting an ingress while agent history survives; and transport policy and behaviour policy are audited separately.

Apps appears twice on purpose. Under Main it is where everyone uses published dashboards; under Build it is where administrators create them.

Main

Chat

The authenticated host chat and the default start page. Users talk to the Agents they have access to in persisted, scoped sessions, with file attachments and a visible activity trail of tool calls. Context compaction keeps long sessions inside the model's context window. Microphone dictation is available when a speech-to-text model is configured.

Apps

The catalogue of published dashboards, open to every active signed-in user, including the user role. A dashboard opens at full width with no layout or editing controls. Each tile has its own form, Run and Run again, execution state, error and result. One failed tile does not block the others, and two users, or two instances of the same process, never share results. A window keeps the dashboard release it was opened with; the next visit loads the latest one. Administrators can jump to Edit in Build.

Inbox

A per-user message box. Agents and scripts deliver results here through the Inbox Delivery tool profile, and budget alerts arrive here too. The navigation shows the unread count. Every user can reach their own inbox.

Assistant

A host-side administration assistant with its own identity, configuration and private conversations per administrator. It is not a hidden Agent and cannot be exposed through an ingress. It shares the Agent turn engine and the Chat presentation, so every tool call, change and result stays visible after a reload.

AreaWhat the Assistant can do
AgentsInspect and configure models, integrations, tool profiles, guardrails and attached data; run private test turns and check readiness
Scripts & AppsFind or create scripts, edit drafts with diff and undo, run an exact draft snapshot, read logs and results, then fix and rerun; carry processes and dashboards through to a tested release
Knowledge & dataCreate Links sources, import URLs, index and refresh, build Rolling knowledge bases and test retrieval
ResearchSearch documentation through pinned Brave Search and Jina Reader revisions
DiagnosticsRead-only view of system state, queues, usage, budgets, logs, Ingress and WebWidget

Changes to egress or bindings, publishing, scheduling, runs of published versions and draft runs that need network access are proposed as approval cards in the conversation and wait for the administrator's decision. Every mutation re-checks permissions and the resource version first. Turns can be stopped; closing the browser does not interrupt work. Ontology editing, Ingress changes, Inbox and user management are out of the Assistant's scope.

Build

Agents

An Agent is a host-side configuration record that defines behaviour. It is not a running process. Each Agent carries:

SettingWhat it controls
ModelLLM provider and model binding, reasoning effort where the model supports it, output-token cap, tool-iteration limit
PromptSystem prompt, context window and compaction: Priority (keeps constraints, compacts low-value tool context first), Summary or Naive, starting at a set share of the window (80% by default)
Internal toolsHost-side knowledge tools (knowledge_search, knowledge_read_document, read_chunk) and the optional Knowledge Reranker, which ranks files found across several searches and bases before the Agent reads them, using an OpenRouter reranking model or a TypeSafe Decision Model
ResourcesAttached integrations (Brave Search, Jina Reader, each pinned to a version), tool profiles, knowledge bases, datasets, Data Products and ontologies. Each is attached explicitly, so the Agent can only use what is listed.
SecurityInbound guardrails and outbound PII filters per surface: Internal Chat, WebWidget, API and Content Processing. Results from tool profiles and knowledge are scanned before they enter the model context, in Balanced mode (all content) or Fast mode (cached, sampled for long results)
ReleasesChanges are edited as a draft and published as a release; earlier releases stay unchanged

The agent flow canvas shows the resulting topology: which ingresses, guardrails, tools and data sources sit around the Agent.

Scripts

Non-interactive Python that runs in a fresh Firecracker VM with no network card attached. A script declares validated JSON input parameters and keeps versions, run history and console output. Runs are admitted as durable background jobs; stopping, timing out or finishing tears the VM down. Scripts can call Agents and use integrations such as Jina Reader, SSH and TypeSafe. To give a script a form, a result view or a schedule, wrap it in an App. Script access follows role assignments: resource_viewer can inspect a script and its runs, resource_editor can edit it, and resource_publisher can publish it.

Apps

Where administrators build what users later open under Main → Apps. New offers two types.

TypeDescription
ProcessWraps one published Script or Agent version in a typed input form and output blocks, with an output schema validated host-side. An Agent process gets task instructions and runs to completion without follow-up questions; a form can accept up to eight files of 20 MiB each. Result blocks include Text, Files (with PDF preview), Line and Bar charts, and Alerts. Each run has its own session and a timeout of 1–3600 seconds. Tabs: Widget, Runs, Settings, Versions.
DashboardComposes process widgets on a 12-column grid: drag, resize or set position by keyboard. Each tile has a title, pinned process release, start mode (manual or on_open) and default parameters. Tabs: Layout, Preview, Settings, Versions. On a phone the grid collapses to one column.

Versions chain explicitly: Dashboard release → Process release → Script release. A new script or process release never changes a published App on its own; the author picks it in the draft, sees it in the diff and publishes. Editing and Preview never execute code; running is always an explicit action. Restore publishes an earlier release as a new version.

Ontologies

Not in the navigation yet

Ontologies are being prepared for release and are hidden from the menu in the current version. The description below covers how the module works.

A model of business concepts (object types, their properties and the relations between them) described before any data is connected. Ontologies describe schema only; they do not store records. Publish creates an immutable version. An Agent that has an ontology pinned gets four read-only tools: ontology_list, ontology_search, ontology_get_type and ontology_explore. Administrators only.

Operations

Ingress

An Ingress exposes one Agent to the outside. Agents without an ingress are reachable only through the host chat.

KindDescription
APIOpenAI-compatible endpoint at POST /ingress/{slug}/v1/chat/completions, with API keys, network access rules and its own guardrails
WebWidgetA browser chat widget served by the separate chatwidget edge service through a tunnel, with session limits, theming and embed code

Scheduler

Scheduled tasks run published Apps. A task holds a name, the App, its parameters, a five-field cron expression and a timezone, and can be enabled or paused. Instead of writing cron by hand you can describe the schedule in plain language (“every Monday at 10:00”) and the Assistant fills in the form; saving applies it.

  • Missed runs coalesce to the latest due time; overlapping executions of the same task are skipped.
  • Future runs use the latest published App and the saved parameters. Editing cancels queued executions; running ones continue.
  • Run now uses the saved configuration and does not move the next cron time.
  • Tasks run with the permissions of the administrator who last saved them. The Activity list links every execution to its logs.

Budget

Two dashboards: LLM Token Spent by Agent, ingress and knowledge source, and Other Usage for filters, the Assistant, audio and retrieval requests. Monthly budgets cap input tokens, output tokens and requests for the whole installation or selected scopes, with a month-end forecast and alerts delivered to chosen recipients. Before every paid model call the host records a conservative pre-charge, then corrects it with the real counters when the response arrives. Calls with missing or estimated usage are counted separately.

Logs

Structured logs for every runtime path: LLM calls, tool calls, guardrail verdicts, RAG indexing and inference, ingress and widget sessions, script, App and scheduled runs, and operational configuration changes. Entries link to each other, so a blocked request leads to its ingress, session and model call.

How to start/Login & authentication

Login & authentication

The host GUI is the administration console. Access to it is the first boundary in the platform, and it is enforced entirely by host code.

Reaching the console

TakeAny.AI binds to 127.0.0.1:3000 by default, overridable with -http-listen. On first run you create the initial host user; subsequent access is through the sign-in form, which establishes a session.

Password storage

Host user passwords are hashed with Argon2id — one-way, never recoverable — with parameters m=65536, t=3, p=2. A password is a credential, not a secret: it can be verified but never decrypted.

Sessions

  • Session token hashes are stored in host_sessions; the raw token lives only in the browser cookie.
  • CSRF tokens are required on all browser mutations.
  • Same-origin checks apply on unsafe methods.

These four controls — hashed passwords, hashed session tokens, CSRF protection and same-origin enforcement — are the host admin boundary. Everything an administrator does in the console passes through it.

Single sign-on

With an OpenID Connect provider configured, the sign-in page offers Sign in with … next to local login. SSO accounts have no local password. Critical changes, such as publishing a role or activating an access proposal, ask for fresh authentication: a password for local accounts, or Confirm with SSO, which sends the user back to the identity provider. Signing out of TakeAny.AI does not sign the user out of the provider. Configuration and group mapping are described in Access & identity.

Note

The console is bound to localhost by default. Exposing it beyond the host is a deliberate deployment choice, not the default — front it with your own reverse proxy and network controls when you do.

How to start/Access & identity

Access & identity

Access in TakeAny.AI is a set of role assignments. Each one gives a user, a group or an Ingress a role on a scope. Grants add together; additional policies can only narrow what they allow. Identities and group memberships can come from your directory through OIDC single sign-on and SCIM provisioning.

Roles, scopes and assignments

A role is an explicit list of operations. An assignment binds one role to a scope: the platform, one concrete object, or type:* for every current and future object of that type. Missing scope selectors are rejected and there are no operation wildcards. Every protected route, stream and background job is checked host-side by an embedded Open Policy Agent (OPA) engine. Policy errors, unsupported contracts, incomplete identity facts and timeouts refuse the operation.

The setup bundles resource_administration, session_files, execution_and_content, network_use and ingress_chat are read-only built-in roles. admin does not directly grant execution, content, network use or resource editing, but an administrator can grant these to themselves, so the role is root-equivalent in practice.

Initial setup

  • Setup creates three ordinary, editable groups: admins, chat_users and power_users. All three receive panel_access, plus agent_user and session_files on agent:*. admins also receives admin; execution, content and network bundles go to admins and power_users.
  • New local users receive a direct panel_access assignment at creation. New OIDC and SCIM users receive no direct assignments; map an IdP group to a local group that carries panel_access.
  • Removing effective panel access blocks login and existing browser sessions without disabling the account or removing execution grants. Login, synchronization and restart never restore a removed assignment.
  • The installation root is a protected local account with its own direct admin and panel_access assignments. It cannot be disabled, deleted or replaced, and a forgotten password is reset offline with takeanyctl auth recover-root, without the identity provider.

Execution belongs to the recipient

An Agent binding is a configuration ceiling, not a grant. Every tool, integration, Script, workflow, knowledge source, dataset, data product, ontology and network request also needs a current positive grant for the original recipient: a verified person with their current groups and SSO evidence, or an API or WebWidget Ingress with its own explicit assignments. The Agent author, the job executor and an administrator retrying a job never supply fallback authority.

  • The Ingress creation preview and Users → Access compare published Agent dependencies with recipient grants and show blocked sources, missing grants and restrictions. A preview does not admit execution; dynamic arguments and network destinations are still checked at runtime.
  • Dataset read, query and export are independent permissions; export is rechecked for every streamed chunk.
  • Protected results keep references to their sources through history, copies, Script results and compaction. Revoking a source blocks reuse of everything derived from it.

Custom roles

Open Governance → Roles. Built-in roles are read-only; Clone as editable opens a prefilled custom draft without changing the source role or its assignments. A role is either a platform role or a resource role, with a name, a description and explicit actions; compatible scope types follow from the actions. For example, an Agent reviewer can hold agent.view and agent.test without agent.edit or agent.publish.

  • Custom roles cannot contain global administrative operations. system.view remains available for a read-only platform role.
  • Save draft changes no access. Under Versions, Validate and preview lists added and removed actions, scope changes and affected users, including known external group members.
  • Apply change rechecks current access and revisions; a concurrent change requires a new preview.
  • Assign the published role from Users → Assignments or Groups → Access. The assignment references the stable role, so a later publication updates every existing assignment.
  • Unknown actions are rejected and new application actions are never added automatically. A scope cannot be removed while assignments use it. Restoring a prior version creates a new immutable revision.

Network access

network.use is assigned only on a concrete, named Network access rule: hosts, CIDRs, ports and host or CIDR exclusions. The resolved IP and port are checked too. Network grants are always intersected with the published execution ceiling of the Tool Profile, Script or Workflow and with every active restriction; granting example.com:443 cannot widen a Browser or HTTP Client profile. Editing a rule requires network_access.manage; rules are versioned and audited separately from roles.

Execution egress is default-deny. Restrictions under Governance → Policies → Execution egress narrow the approved ceilings with Rego rules over host observations (host, ip, port, transport, and method and path for HTTP requests). Every request, redirect and reused connection is authorized again, and live sockets are revalidated every 250 ms; the local revocation bound is two seconds.

package takeany_custom
import rego.v1

default allow := false
allow if input.observation.fields.host.value in {"api.example.com", "r.jina.ai"}

Single sign-on (OIDC)

TakeAny.AI signs users in through an OpenID Connect provider, using the Authorization Code flow with mandatory PKCE (S256). Microsoft Entra ID, or Keycloak in front of Active Directory, are typical choices. Configuration lives in the database and only the installation root can change it.

Host

Set the public origin

Start with --host-public-url (or TAKEANY_HOST_PUBLIC_URL). The callback URL is derived from it, never from the browser.

Secrets → New

Store the client secret

Create a secret of type OIDC client secret. Its value is never shown again.

Settings → General → Single sign-on

Save a draft

Enter provider key, display name, exact issuer and client ID, select the secret and set admission rules. Saving a draft leaves active logins unchanged.

Settings → General → Single sign-on

Test, then activate

Test saved draft authenticates a real user without creating an account. Activate tested draft within ten minutes; it takes effect without a restart.

  • Admission rules combine: allowed tenants (Entra tid), allowed subjects and allowed email domains (verified email, exact match). Account creation on first login must be enabled explicitly.
  • A new SSO account has no password and no direct roles. An existing local account is linked explicitly from Profile → Single sign-on, keeping its ID, memberships and grants. Accounts are never linked by email.
  • session_seconds defaults to 8 hours (60 s to 24 h). TakeAny.AI does not request offline access and keeps no access or refresh tokens.
  • A local block is authoritative: an IdP login does not undo it. Local root login keeps working when the IdP is unavailable; --sso-disabled disables the provider for recovery.
  • A legacy JSON file passed with --oidc-config-file can be imported into the draft explicitly. It never overwrites active settings on startup.

Mapping directory groups and App Roles

Group membership stays where you govern it today: Active Directory, Entra ID, or an IAM or IGA system. Create local groups under Governance → Groups, give them role assignments, then map stable external identifiers to them under Group mappings in SSO settings. The equivalent import fragment:

{
  "account_max_age_seconds": 900,
  "membership_max_age_seconds": 900,
  "group_mappings": [
    {"claim": "groups", "external_id": "EXTERNAL-GROUP-ID", "group_id": 12},
    {"claim": "roles",  "external_id": "Reports.Reader",    "group_id": 13}
  ]
}
  • A groups value or an Entra App Role in the roles claim maps to a local group, whose assignments decide the permissions. Entra directory roles (wids) are ignored. Up to 200 mappings and 200 values per claim.
  • The startup admins group contains local root and cannot be mapped. Use an empty dedicated group such as idp-admins for IdP administrators.
  • Each group has one membership source: Local, OIDC or SCIM. External memberships are read-only in TakeAny.AI and never remove a local membership or a direct grant.
  • A missing, null or malformed claim, or a group overage indicator, refuses login instead of being read as an empty list.
  • Account and membership evidence is valid for 15 minutes by default (60 s to 24 h). After that, new requests and running work stop until the user signs in again. A newly observed administrative membership requires authentication no older than five minutes.
  • Mapping changes apply on activation and require affected users to sign in again.
What the mapping covers

Memberships are read from the token at each sign-in; TakeAny.AI does not call Microsoft Graph. Changes in your directory take effect at the user’s next sign-in, and at the latest when the freshness window expires. For changes between sign-ins, use SCIM provisioning.

SCIM provisioning

SCIM 2.0 provisions external accounts and mapped group memberships independently of login. OIDC still authenticates the person; local roles and OPA decide their rights. SCIM cannot create roles, import root, assign arbitrary permissions or remove a local block.

  • Create a separate SCIM bearer token secret (at least 32 random bytes), enable SCIM in SSO settings, choose the identity binding and map external group IDs to local groups. The endpoint is https://<host>/scim/v2.
  • externalId equals the verified OIDC sub, or the Entra object ID (oid) with a fixed tenant. No account is adopted by email; collisions return 409.
  • Users and Groups support GET, POST, PUT, PATCH and DELETE with ETags. DELETE leaves a tombstone that blocks reprovisioning with the same externalId.
  • Membership removal and deactivation cancel dependent jobs and close active connections within two seconds of the local commit.
  • max_age_seconds (default 24 h) bounds provisioning liveness. On expiry, SCIM-dependent decisions and new SSO sessions fail closed; root and local accounts remain available.
Treat the token as privileged

The SCIM token can add members to mapped groups that carry admin, without interactive reauthentication. Review every mapped group’s roles before enabling provisioning.

Additional policies (OPA / Rego)

Open Governance → Policies. A policy is an additional_restriction: it can deny what roles allow, never grant. Managing policies requires admin. Three contracts are implemented:

ContractRestricts
takeany.policy.agent-use/v1Agent use by subject (user or Ingress), groups and channel. Attached to specific Agents
takeany.policy.runtime-use/v1One stable execution resource: its type, ID, recipient, groups and channel
takeany.policy.runtime-use/v2Selected Agents and operations, host tool operations and validated arguments (Brave Search, dataset query and export, data product query)

Channels are gui, api, webwidget, script, scheduler, assistant and internal, established by the host. This policy restricts members of group 7 to the GUI and leaves other users unchanged:

package takeany_custom
import rego.v1

default allow := false
restricted if { some m in input.memberships; m.group_id == 7 }
allow if { not restricted }
allow if { input.context.channel == "gui" }
  • Up to 64 test cases with expected results. Compilation and every test must pass before publication.
  • Previews evaluate current users and real API and WebWidget Ingresses, bounded to 2,000 decisions; split a broader change instead of accepting a truncated preview.
  • Agent restrictions apply to current and historical releases, and to Script and Scheduler calls of that Agent.
  • Disabling, relaxing or removing a restriction requires authentication within the last 30 minutes.
  • Limits: 32 KiB of Rego, 500 expressions, 100 rules, 1 MiB of input, 20 ms evaluation. Only deterministic built-ins are available, with no access to secrets or other packages.

Knowledge source access

Open a knowledge source and choose Access. Prevent public access is on by default: API and WebWidget Ingresses cannot read the source even with a read grant. Unchecking it grants nothing; the Ingress still needs knowledge.read on that source.

  • Platform users always need their own current Knowledge Reader grant. Attaching a source to an Agent or a Knowledge Base does not grant access to its contents.
  • When creating a source, an administrator can create a dedicated reader group and manage its members from the source’s Access tab.
  • Full-text and semantic search filter sources before ranking, so unauthorized content never reaches the model. Citations, originals and derived copies check the same permission.
  • A conversation rechecks its sources on every turn. Losing access blocks further use of that protected context.

Administration and fresh authentication

Assign admin once with platform scope, normally to a group. There is no separate delegation or ceiling form: resource roles stay scoped to one object or one type, and global administration is reserved for built-in roles.

  • Security mutations require authentication no older than 30 minutes: permission removals, password resets, IdP secret changes, network rule edits and restriction removal. Activity does not extend the window.
  • A local session confirms its password in a dialog; an SSO session goes through the identity provider and returns to the page. Reauthentication rotates that session’s token.
  • secret.bind authorizes selecting a Secret in a resource configuration; secret.view only shows its metadata. Recipients use delegated credentials through their execution rights and need neither.
  • OIDC client secrets and SCIM tokens are dedicated identity provider secrets, managed only with admin and never bindable to resources.

Describe access with the Assistant

Describe access with Assistant in Roles or Policies, or /access/assistant, turns a sentence such as “Finance can use the Reports Agent only through the GUI” into a takeany.access-proposal/v5 proposal: assignments, custom resource roles, Rego, tests, network rules and knowledge read grants. The host validates every reference and evaluates real before and after scenarios, bounded to 2,000 scenarios and two seconds.

  • The proposal is private to its author and is applied as a whole, in one transaction. Any failed validation rolls the whole set back.
  • Account and SSO changes, global administrative roles and the author’s own access remain manual.
  • An ambiguous request produces a clarification question; the answer creates a new immutable proposal.

Audit and revocation

  • Logs → Access Audit records drafts, publications, restores, attachments, assignments, mappings and network decisions with the actor and before and after state.
  • Users → Access summarizes granted permissions with their sources and includes an operation tester that can simulate ignoring a group or adding a role, without saving changes.
  • Running Agent turns, streams and background workers recheck access every 250 ms. Unauthorized work stops within two seconds of the change.
  • At startup TakeAny.AI verifies active role and policy versions and checksums. Invalid active state stops startup instead of falling back to an older, less restrictive revision.

How to start/Security & compliance

Security & compliance

Five independent boundaries, each enforced by host code and each independently logged. Compliance evidence is a by-product of running the system.

Secrets

Two distinct policies, correctly separated:

  • Recoverable secrets (provider keys, SSH credentials) — AES-256-GCM with a 12-byte nonce, sealed under TAKEANY_SECRETS_MASTER_KEY, which must decode to exactly 32 bytes. Ciphertext and nonce are stored in separate columns.
  • Credentials (host user passwords) — Argon2id, one-way, never recoverable.

Secrets referenced by helpers use ON DELETE RESTRICT: a secret in use cannot be deleted out from under a live integration.

LLM safety firewalls

Firewalls are model-based evaluators applied at message boundaries. Three kinds exist — generic_judge (custom prompt), llama_guard and shield_gemma — each with a direction (inbound or outbound), its own provider and model binding, a policy prompt and a refusal message.

Firewalls attach at two levels: embedded chat on the Agent, and transport on the Ingress. A public widget can therefore run stricter evaluation than the same agent's internal use. Verdicts are logged to firewall_logs, and a test endpoint lets you tune policy before deployment.

A defence layer, not a guarantee

Firewalls are model-based evaluators and inherit the reliability characteristics of the models running them. Treat them as one layer among five, not as a promise.

Network controls

Execution egress is default-deny and evaluated by embedded OPA on the host. Python and Browser proxies, HTTP Client, Script integrations and knowledge imports all pass through it; helpers have no external network interface. The host resolves DNS and checks every answer before dialing, and admissions and denials are recorded in Logs → Access Audit without URLs or payloads. See Access & identity for Network access rules and egress restrictions. A controlled subset of host APIs — /llm, /knowledge, /helpers, /environment — is exposed to guests, with provider keys injected host-side at that boundary. This is the mechanism by which a guest can use a model without ever holding a credential.

Knowledge & retrieval

Knowledge bases are host-owned. Documents are ingested and chunked in an isolated one-shot workload, then indexed for host-side retrieval; the chunk and inference prompts are configurable per corpus. Retrieval executes no guest code, and knowledge_usage_logs records which documents answered which query.

The public edge

The chatwidget edge service is a separate binary intended for DMZ deployment. It holds no database access and no credentials. Its controls include HMAC-derived slugs, a shared-key authenticated tunnel, origin checks, request and message size limits and a per-IP ban window. The tunnel is outbound from the TakeAny.AI host — the public edge cannot initiate a connection inward.

Observability

Fourteen log domains record runtime activity: agent turns, tool calls, every model request (with token counts split into prompt, cached, completion and total), firewall verdicts, helper executions, job events, knowledge retrieval and sync, workflow runs and steps, proxy traffic, remote commands and authorization decisions. For any answer an agent gives, the retrieved context and the spend behind it are recoverable.

Compliance posture

TakeAny.AI gives your compliance team full data lineage without a documentation project: what entered the prompt, what was retrieved, what the model returned, which tools ran and what it cost — recorded as a by-product of operation.

Under the EU AI Act, Article 50 transparency duties take effect 2 August 2026. Annex III high-risk obligations now run to December 2027. Building the evidence base into the architecture — rather than bolting it on later — is what these dates reward.

On compliance claims

No tool delivers regulatory compliance on its own; compliance is an organisational obligation. What TakeAny.AI provides is the evidence base — lineage, attribution and audit — that a compliance programme is built on.

Solutions/04.3 Build an App with the Assistant

Build an App with the Assistant

Describe what you need in one message. The Assistant writes and tests a Python script, wraps it in a process App and adds it as a widget to a dashboard, asking for approval before each change is published. This example builds a calculator that sums two numbers.

Nothing is published without approval

The Assistant prepares drafts and runs them, but every publication waits for Approve. Each change it makes is a normal draft or release that you can review, edit or restore later in Build.

Before you start

  • An administrator account and a model set for the Assistant. See 03.1 Basic Setup, step three.
  • A dashboard to attach the App to. The example uses dashboard 997.

Reference/Glossary

Glossary

Terms used in the TakeAny.AI console and in these docs, in alphabetical order.

A – C

TermMeaning
Access assistantTurns a plain-language access request into a reviewed proposal of assignments, roles and policies, activated only after fresh confirmation.
Additional policyA Rego rule attached to Agents that can only restrict access allowed by roles, for example to one channel.
AgentA host-side configuration record defining behaviour: model, prompt, tools, knowledge and safety settings. Not a running process.
Agent releaseA published, immutable snapshot of an Agent draft. Ingresses serve the published release.
API ingressAn OpenAI-compatible endpoint exposing one Agent, protected by API keys and network rules.
AssistantThe built-in administrator assistant that builds and changes scripts, Apps and dashboards in chat, and asks for approval before publishing.
Association RecommenderA Data Product that finds products bought together and recommends complements.
Audit logThe structured record of what happened: model calls, tool calls, verdicts, changes.
Background jobA durable queued task (data builds, scripts, knowledge indexing) with retries and history.
Browser ControlA tool profile that runs a full Chromium browser for an Agent inside a Firecracker session. The only browser profile that supports saved website logins, which the host fills in without the Agent seeing them.
Browser Control LightA lighter tool profile with the Obscura browser for public websites, with screenshots and PDF output and no login tools.
BudgetMonthly limits and accounting of token usage per provider and Agent.
CeilingThe approved configuration limit of an Agent, Tool Profile, Script or Workflow. Recipient grants and restrictions apply within it; a grant can never widen it.
ChatwidgetThe separate edge service that serves the public WebWidget, typically in a DMZ.
ChunkingSplitting documents into passages before they are indexed for retrieval.
Context compactionShrinking a long session to fit the model’s context window. Three modes: Priority (keeps constraints, compacts low-value tool context first), Summary and Naive.

D – I

TermMeaning
DashboardA grid of process widgets with pinned versions, start modes and default parameters. Published dashboards are Apps.
Data ProductA versioned, publishable model built from a dataset and exposed to Agents as a typed tool.
DatasetVersioned tabular data (CSV, XLSX) stored in DuckLake and queryable read-only by Agents.
DuckLakeThe catalogue format TakeAny.AI uses to version datasets on top of DuckDB and Parquet files.
Egress proxyThe host-controlled proxy through which isolated workloads reach the network, with domain rules.
EmbeddingA numeric vector representing text, used to find relevant passages in a knowledge base.
Fail closedWhen a check cannot complete, the request is blocked rather than let through.
Firecracker microVMA lightweight virtual machine (KVM) used to isolate risky work such as browsing, rendering and scripts.
Generic JudgeA guardrail type that evaluates a natural-language policy with an LLM.
Group mappingA configured link from an identity provider group or App Role to a local TakeAny.AI group.
Guardrail (inbound)A policy that checks input before it reaches the Agent and returns a refusal message when it fails.
InboxA per-user message box that Agents and scripts deliver results to.
Indirect prompt injectionInstructions hidden in content an Agent fetches (a web page, email or PDF) rather than typed by the user.
IngressThe record that exposes an Agent through a transport: API or WebWidget.
IntegrationA host-side connection to an external service (Brave Search, Jina Reader, SSH, TypeSafe) whose credentials never leave the host. Brave Search and Jina Reader can be attached to Agents; all four are available to Python scripts.
Internal guardrailA guardrail type that runs locally: a structural scanner, then the Wolf Defender Small v2 prompt-injection classifier on CPU in a local sidecar. No external model call.
Isolated runtimeA catalogued Firecracker workload, such as a RAG indexer or the document renderer.

J – P

TermMeaning
Jina ReaderA service that reads a web page and returns clean text, available as an integration.
Knowledge baseA versioned collection of sources indexed for retrieval by Agents.
Knowledge RerankerAn optional Agent tool that ranks files found across several searches and knowledge bases before the Agent reads them, using an OpenRouter reranking model or a TypeSafe Decision Model.
LLM providerAn OpenAI-compatible model endpoint configured in Settings → Providers, with its key stored as a secret.
Mission ControlThe console start page for administrators: Agents, activity, token usage and App schedules.
OIDCOpenID Connect: the single sign-on protocol TakeAny.AI uses with identity providers such as Entra ID or Keycloak.
OntologyA published model of business object types, their properties and relations. Schema only, no records. Hidden from the navigation in the current version.
OpenAI-compatibleUsing the same HTTP request format as the OpenAI Chat Completions API, so existing clients work unchanged.
PII filter (outbound)A check that masks personal data in a response before it is delivered.
Pre-chargeA conservative usage estimate recorded before a paid model call and corrected afterwards.
ProcessA published Script or Agent version wrapped in a typed form and result view. The building block of dashboards.
Prompt injectionAn attack that tricks a model into ignoring its instructions through crafted input.

R – Z

TermMeaning
RAGRetrieval-augmented generation: the model answers using passages retrieved from a knowledge base.
RBACRole-based access control: built-in and custom roles, each an explicit list of operations assigned to a user, group or Ingress on the platform, one object or all objects of a type.
Reader restrictionA rule limiting which users, groups and channels may read a knowledge source or file.
Refusal messageThe text returned to the user when a guardrail blocks a request.
RerankingRe-ordering retrieved passages with a dedicated model so the most relevant come first.
Role assignmentOne role given to a user or group on one scope.
RootThe protected local installation account, independent of roles and of the identity provider.
SchedulerRuns published Apps on a cron expression and timezone, with run history and Run now.
ScopeWhat a role assignment applies to: the installation or one resource such as an Agent, workflow or dataset.
Scratch FSThe temporary file workspace of an Agent session, also used for pinned Agent files.
ScriptA Python program run in an isolated VM with validated parameters and run history. Wrapped in an App to get a form, a result view and a schedule.
SecretAn encrypted credential stored on the host. It can be rotated but never displayed.
SSOSingle sign-on with a company account through an OIDC identity provider.
SurfaceA channel an Agent is used through: Internal Chat, WebWidget, API or Content Processing. Guardrails are set per surface.
System 1 ClassifierA guardrail type backed by TypeSafe that scores six risk categories in one request.
Tool ProfileA configured tool with its own policy and credentials, attached to Agents: HTTP Client, Calculator, Inbox Delivery, Browser Control or Browser Control Light.
TypeSafeA classification provider added under Settings → Providers. Used by the System 1 Classifier, the Knowledge Reranker and Python scripts.
WebWidgetA public browser chat surface for one Agent, served through the chatwidget edge service.
